## 1. 背景

Blocky 的目标是让用户自由搭建不同类型的 Agent，并把 GitHub 项目和现有 Agent 尽可能转换为可编辑积木。只允许声明式积木无法覆盖自定义算法、CLI、MCP、数据库、外部服务和框架独有行为；把所有能力都内置到 Core 又会造成框架专用积木膨胀。

因此，完整产品需要同时支持纯数据模板、可展开组合积木和携带可执行逻辑的扩展积木。开放执行能力会带来供应链、任意代码执行、秘密泄漏、权限升级、依赖冲突和恶意更新风险，不能沿用普通模板的安装模型。

## 2. 决策

### 2.1 四类分发对象

| 类型 | 内容 | 运行边界 |
|---|---|---|
| 纯模板 | 项目片段、Agent、积木、布局和可移植资源 | 只经统一 Schema、类型和权限校验 |
| 组合积木 | 可视化自定义积木：由已有积木封装的可复用能力 | 必须可无损展开并接受相同校验 |
| 扩展积木 | 代码自定义积木、CLI、协议客户端、连接器或外部服务适配 | 必须进入隔离运行与权限流程 |
| 原生兼容包 | 指定上游版本的映射、适配器和官方运行时连接 | 进程隔离、版本锁定并单独完成兼容验收 |

自定义积木不是遗漏语义的“其他”类型，而是完整产品的一等能力：

- **可视化自定义积木**声明名称、外观、输入、输出、默认值、错误和版本，内部由现有积木组成，可展开查看与调试。
- **代码自定义积木**声明同样的外部契约，并额外声明语言/运行时、实现入口、权限、沙箱、资源预算、取消和支持的运行目标。
- 两种自定义积木都能保存、版本化、导入导出和进入社区；从一种实现迁移到另一种时必须保持稳定积木 ID 或提供显式迁移。
- 代码实现只允许封装局部不可约逻辑，不能隐藏 Agent 拓扑、Tool Schema、交互入口或宿主权限。

### 2.2 可执行扩展准入

可执行扩展允许进入 Blocky 社区，但每个版本必须具备：

- 稳定包 ID、语义版本、内容摘要、发布者身份和签名。
- 源代码或可审查构建来源、许可证、依赖锁和运行环境声明。
- 文件、网络、进程、设备、秘密、外部账号和副作用权限清单。
- CPU、内存、磁盘、网络、进程数、执行时间和并发预算。
- 输入/输出 Schema、稳定错误类型、取消协议和敏感信息处理说明。
- 安装前扫描、运行时隔离、超限终止、签名撤销和恶意版本下架能力。

签名只证明发布者和内容未变，不能代表代码安全或官方背书。安全扫描通过也不能替代权限展示与沙箱。

### 2.3 安装与更新

- 安装前展示来源、许可、代码状态、权限、依赖、运行环境和已知风险。
- 项目生成精确版本锁；依赖求解失败必须报告冲突，不静默换版本。
- 更新先比较代码摘要、权限、依赖、Schema 和迁移影响。新增权限必须重新确认。
- 社区版本下架后，本地锁定副本按许可证保留；被确认恶意的版本默认禁用执行，但不破坏项目数据，用户可查看原因和导出内容。
- 卸载只删除由包管理器拥有且摘要匹配的文件，不删除用户派生内容或共享依赖。

### 2.4 隔离与 Host 授权

- 不受信任代码不得在 Blocky 主进程、WebView 或具有完整用户权限的普通本机进程中直接运行。
- Windows 首选受限子进程、容器或经过验证的 WASM/远程沙箱；具体机制由技术尖峰和威胁模型决定。
- Android、HarmonyOS、macOS 和 iOS 必须使用各平台可证明的隔离能力；不能把 Windows 方案名称直接当作跨端保证。
- 沙箱内仍需最小能力代理。文件、网络、秘密和设备操作通过 Host Contract 提供，扩展不能自行扩大范围。
- 发送消息、写外部系统、删除、支付、发布和原生配置写回继续要求短期、单次、作用域授权。
- 交互入口积木把 Skill 或插件动作显示在右侧输入栏，只代表“允许用户看见并发起”，不代表扩展已安装、已信任或取得运行权限；调用时仍执行完整的版本、沙箱和授权检查。
- Android、HarmonyOS 与 iOS 只有在目标协商确认扩展可在该设备沙箱运行时才允许本地执行；否则必须明确连接桌面或服务器运行端。

### 2.5 与原生兼容适配器的关系

Pi、Codex、OpenClaw、Hermes、OpenCode、DeepSeek Harness 等原生兼容适配器不因“官方内置”而绕过隔离、权限、版本和行为验收。社区扩展也不能冒充系统适配器取得更高权限。两者可以复用包格式和 Host Contract，但使用不同信任标识与验收等级。

## 3. 取代的旧约束

本 ADR 取代 ADR-001 和 ADR-002 中“第三方积木包不得携带任意代码”的绝对禁止。新的边界是：允许可执行扩展，但必须与纯模板分型，并通过签名、扫描、版本锁、隔离、资源预算、权限和可撤销授权共同约束。

## 4. 后果

### 正面

- 通用积木保持精简，框架或业务独有能力通过扩展实现。
- GitHub 项目转积木和现有 Agent 逆向不必把无法表达的代码压成不可运行说明。
- 社区可以形成真实能力生态，同时保留来源、许可和权限透明度。

### 成本与风险

- 需要跨平台沙箱、包签名、恶意代码分析、依赖求解、撤销和安全响应系统。
- 行为可重复性会受到外部依赖、运行时和网络影响，必须记录完整环境。
- “可安装”不等于“安全”或“高质量”，产品必须保持清晰来源和信任等级。

## 5. 验收门槛

- 纯模板和组合积木不执行包内任意代码。
- 可视化自定义积木可展开且与展开后的类型、权限和运行结果一致。
- 代码自定义积木缺少类型、错误、权限、沙箱、预算或运行目标任一契约时拒绝安装或编译。
- 扩展无法访问未声明文件、域名、秘密、设备或进程能力。
- 仅把 Skill/插件动作暴露到交互入口不会授予执行权限。
- 资源超限、取消、崩溃和恶意退出不会带走 Blocky 主进程或破坏项目文件。
- 包内容、签名、权限和依赖任一变化都会改变摘要并触发重新审查。
- 更新、撤销、下架和卸载均保留用户项目及可解释状态。
- Windows 技术尖峰证明隔离边界后才能选择正式实现；其他平台分别验收，不能外推。
