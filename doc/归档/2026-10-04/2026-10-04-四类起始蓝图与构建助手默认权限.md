# 四类起始蓝图与构建助手默认权限

状态：2026-10-04 用户已确认按本设计实施并验收，包含 B01–B08 与独立验收角色。四个蓝图完成前不再进行发行构建。

## 用户目标

内置蓝图按固定顺序提供：知识问答助手、工作助手、Coding 助手、Pi Agent。它们是可编辑的普通 Blocky 项目起点，用户能够改变角色、模型、资料、工具、上下文、触发方式和输出，把通用底座改造成专项 Agent。旧 16 个起点及旧六品牌交付路线退出当前产品目录。

Pi Agent 使用真实上游 Agent 核心。用户已明确选择核心积木化，不包含完整 Pi 编程 CLI 的终端界面、任意 Shell 或全部插件兼容。内置构建助手默认可操作当前项目和 Blocky CLI；发送任务即开始执行，不再额外弹出代码助手任务批准窗口。工作目录能力按已选择目录实际可用性判断，不能把未选目录误报为当前项目无权限。

## 架构依据与已核对的缺口

- [Anthropic 主流架构说明](https://www.anthropic.com/engineering/building-effective-agents)：按任务需要组合检索、工具、反馈循环和固定工作流，保留可理解的基础结构。
- [OpenAI Agent 实践指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)：模型、工具、指令和执行边界构成可扩展底座。
- [Pi Agent 0.86.0](https://github.com/earendil-works/pi/blob/v0.86.0/packages/agent/README.md)：实际 Agent 类负责模型与工具循环、上下文和事件；映射对象是这些运行语义。
- Pi 上游锁定 `earendil-works/pi`、tag `v0.86.0`、commit `ecac0a9c4edad3dac5d9f8b40e0c7db7a56471fc`、MIT；本项目已有同版本 `@earendil-works/pi-agent-core` 和 `pi-ai`。实施时保存来源、源码哈希、依赖与映射证据。
- 现有构建助手真正使用 Pi；作品的 `core.reason.tool_loop` 是 Blocky 自有循环。后者不能仅改显示名成为 Pi 蓝图。
- 文件列表、检索、读写、撤销和 Blocky CLI 工具目前主要在构建助手中。工作/Coding 作品须接入共享受控工具，不能把文字统计或空工具清单当作文件工作能力。
- 旧资料起点在空资料库上直接检索，会产生无索引错误；新的知识蓝图必须具有准确、可操作的配置状态和真实资料闭环。

## 四类蓝图

| 顺序 | 蓝图 | 默认结构 | 可改造方向 | 必须证明的实际行为 |
|---|---|---|---|---|
| 1 | 知识问答助手 | 聊天入口 → 角色/预算 → 资料检索 → 证据约束 → 模型组织 → 引用回答 | 产品手册、课程、法规资料、个人文档检索 | 导入和同步真实合成文件后回答可核对原文；无命中、未同步、撤权各有准确结果 |
| 2 | 工作助手 | 任务入口 → 工作要求/上下文 → 工具反馈循环 → 会话记忆 → 交付物 | 资料整理、报告生成、专项重复工作、连接工作流 | 在所选测试目录读取实际资料、生成文件并提供回执；修改角色/工具后完成第二个专项任务 |
| 3 | Coding 助手 | 任务入口 → 仓库上下文 → 搜索/读取/修改 → 工具反馈 → 检查 → 差异与结果 | Blocky 项目及普通代码的专项开发助手 | 实际修改合成仓库、执行已支持检查、失败能反馈修正、保留差异与撤销；未支持的检查需通过声明工具扩展 |
| 4 | Pi Agent | 入口 → system prompt/上下文 → 模型 → 工具声明 → 真实 Pi Agent 循环 → 输出 | 用户自定义工具、会话策略与角色的基础 Agent | 上游 Agent 实际执行模型→工具→后续模型；配置往返、会话隔离、预算及取消有证据 |

蓝图中的角色和默认工具可以删除、替换或添加，不能依赖固定题目或预写答案。模型采用用户真实配置，缺少模型或工具授权时显示具体配置缺口。知识蓝图不附带伪装成用户资料的示例知识库。

## 共享实现边界

1. 新目录只注册四个稳定 ID，桌面和 CLI 读取同一目录与工厂；空白新建保留。新 ID 与旧 ID 区分，旧目录不通过别名继续出现。
2. 蓝图保存普通 Manifest、Workspace、资源引用及公开插槽。原子积木支持展开、改造、保存为个人蓝图及重新打开；来源元数据不包含本机路径或密钥。
3. Pi 循环通过 Host 的模型和工具端口运行。Pi 本身不持有模型凭据，也不绕过资源验证、工具输入输出 Schema、调用预算和取消结算。通用核心积木 ID 不使用框架品牌命名；引擎选择及来源详情明确绑定真实 Pi。
4. 复用构建助手已有文件 Scope 与差异/撤销机制，提供作品所需的共享工作目录工具。工作目录由用户选择，项目只引用本机绑定；未选目录不影响纯聊天、当前项目上下文和 Blocky CLI。
5. Coding 的检查工具以明确的命令、参数、范围、时限和输出回执执行，复用 Host 进程管理；不能把模拟成功、只生成检查计划或无结果返回写作验证通过。通用 Shell 与全部语言生态不作为本轮默认能力声明。
6. 运行日志、当前项目诊断和最近失败摘要作为构建助手的可用上下文，使用有界、脱敏的数据契约；资料或日志中的文本不授予新权限。
7. 需要配置的蓝图先显示模型、资料、工作目录或工具的具体缺口。桌面有直接配置入口，CLI 有结构化状态；不能启动后只给出“运行失败”或猜测权限不足。

## 构建助手默认体验

- 默认提供 `project_context` 和 `blocky_cli`，能力说明反映真实可用工具。用户没有选择工作目录时仍能问候、解释当前积木、读取当前诊断和运行失败。
- 去掉发送任务时的原生批准弹窗；用户已有模型配置与发送行为是本轮任务启动依据。保留真实错误、停止、差异和版本冲突处理。
- 当前项目的有效修改默认应用为一次可撤销编辑。项目已发生并发修改时保留候选并明确冲突，不覆盖用户新修改。
- 选定工作目录后，文件工具直接在所选范围执行并保留差异和撤销；不因每条聊天重复要求授权。
- 回复简洁，说明已执行操作与结果。缺少具体能力时只指出该能力，不概括为“没有工作区/项目权限”。

## 实施与构建顺序

1. 收束并记录旧模板清理检查点，保留测试夹具、用户资料和个人蓝图。
2. 完成 Pi 运行桥接、共享文件/检查工具及构建助手默认权限与上下文。
3. 完成四个普通项目蓝图、配置状态、桌面与 CLI 入口；同步当前规则和路线。
4. 运行最小充分的类型、组件、领域、Host 与 CLI 验证，修复本轮影响范围的问题。
5. 四个蓝图完成后构建普通 Windows 包，独立验收实际包；验收通过后交付。main 合并、分支清理和 push 仍遵循团队项目的既有授权规则。

## 更新后的验收草案

采用 L3：本轮增加作品文件操作、真实 Pi 引擎及构建助手默认执行行为。最终由未参与实现的 sol 独立执行；安全和隐私相关检查按用户规则使用 high，其余普通功能可沿用已确认的 medium。

| 编号 | 用户功能 | 场景与失败判据 |
|---|---|---|
| B01 | 内置蓝图与改造 | 目录只有四个且顺序一致；创建、改角色/模型/工具、保存重开及个人蓝图可用；旧 ID 不再创建 |
| B02 | 知识问答 | 真实导入同步、正确命中及引用原文；未同步/无命中/撤权结果准确；伪引用、固定答案或泛化失败为不通过 |
| B03 | 工作任务 | 两个不同专项任务在所选合成目录产生真实结果及回执；仅文本演示、未执行副作用或越界访问为不通过 |
| B04 | Coding 任务 | 搜索读改、实际检查、错误反馈及差异/撤销；检查未运行却声称通过为不通过 |
| B05 | Pi 核心 | 官方锁定来源、真实 SDK 循环与工具回传、会话隔离及取消/预算；自有循环改名为不通过 |
| B06 | 构建助手 | 普通包无目录问候、解释项目和失败；默认 CLI 改画布可撤销；发送不出现额外权限窗口；错误权限宣称为不通过 |
| B07 | 执行与数据边界 | 所选目录、并发冲突、取消结算、凭据与日志隔离；越权读写、秘密外泄、遗留进程或覆盖并发修改为不通过 |
| B08 | 普通包交付 | 四蓝图完成后构建，同来源普通包与 CLI 实际复验；旧注册残留、测试后门或来源不一致为不通过 |

以上表格为实施前已确认的验收草案；完成状态以文末归档说明和独立任务验收为准。
