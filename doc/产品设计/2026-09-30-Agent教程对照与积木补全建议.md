# Agent 教程对照与积木补全建议

## 1. 结论与核对范围

当前积木尚未齐全。0.7.1 已有可运行的资料问答、模型生成、记忆、模块调用、持久审批工作流和有人值守自动化，但距离通用 Agent 搭建平台仍有明显缺口。

本次对照当前源码 `cedf0b0fc77ababb000f81876113090ddc4c3f46` 与普通包 `dist/Blocky-Studio-0.7.1/` 的 CLI 读回；产品来源为 `4f8173e`。普通包 `catalog list --limit 100 --json` 返回 43 种积木、无下一页，目录版本 0.5.0；`template list --json` 返回 11 个项目模板。目录版本与应用版本是不同字段。

本次是源码、命令发现和官方资料核对，没有重新运行所有功能，也没有执行外部教程代码。既有功能验收仍以[0.7.1 任务验收](../验收/任务/验收-2026-09-30-工作区与默认模型.md)及其前置阶段证据为准。真实大模型 API 调用：否（本次调研）。

## 2. 已有能力与实际限制

| 领域 | 当前事实 | 需要补齐的部分 |
|---|---|---|
| 知识摄取 | 文件、目录、锁定仓库和 URL 来源；增量同步、删除、访问控制与引用定位已有实现 | 解析器主要接受文本、Markdown、HTML 和代码；PDF、Office、扫描件 OCR、表格结构化解析尚未接入 |
| 检索 | 关键词、向量、混合检索、元数据过滤、去重、上下文预算与引用核对 | “重排”是检索分数、词项覆盖和标题覆盖的规则评分；还没有可替换的神经重排模型、问题改写与相关性判断闭环 |
| 知识积木 | 画布只有 `core.knowledge.retrieve`；添加来源、同步、嵌入、删除等能力可通过知识管理与 CLI 使用 | 已有领域能力尚未全部成为可组合的摄取积木；不能将“没有积木”误判为“没有底层能力” |
| 嵌入模型 | Host 本地运行锁定的 `multilingual-e5-small-int8-v1`，384 维，校验模型文件，推理不外发 API | 只接受这个模型 ID；需要模型资源选择、维度/版本管理、切换后重建索引与效果对比 |
| 生成模型 | 作品运行支持确定性整理、DeepSeek 和息壤适配器；默认模型引用已经打通 | Host 只允许两家已实现远程端点；尚无通用自定义 Provider、Ollama 或内置本地生成模型。确定性整理不是本地大语言模型 |
| 自主工具使用 | 有显式工具调用、模块调用、RPA 和运行预算 | 作品 Provider 请求只有文本消息，未携带工具集合、工具结果消息或 `tool_calls`；通用“选择工具—执行—观察—再决策”尚未实现。当前通用工具 Host 适配器主要为文本分析，RPA 使用独立受控通道 |
| 构建助手 | 有 inspect/draft/patch/verify 受控工具循环 | 它服务于搭建项目，不能据此宣称用户作品已有通用自主 Agent 循环 |
| 决策与编排 | 状态机、行为树、优先级规则和规则/模型协作是既有原语组合；已有事件队列、持久审批、检查点与补偿 | 尚无可装载的分类、回归或策略模型后端；`parallel` 只允许安全的纯计算类步骤，不能当作并行多 Agent 或并行外部工具 |
| 记忆 | 有会话及项目范围的读、写、删除 | 语义检索、记忆摘要、有效期、冲突合并与来源管理尚未形成完整用户流程 |
| 扩展与评估 | 有资源 Schema、诊断、轨迹、CLI 和开发质量测试 | MCP/Skill 运行接入尚未完成；用户作品的测试集、质量评分、版本对比尚未形成评估工作台 |

## 3. 值得参考的官方完整教程

以下链接于本次调研打开核对。教程中的模型名、安装命令和在线服务版本仍应在实际实施时重新锁定；这里借鉴流程与能力划分。

| 官方教程 | 从头到尾的流程 | 对 Blocky 的具体启发 |
|---|---|---|
| [Dify：创建知识并接入聊天应用](https://dify.ai/blog/create-knowledge-in-dify-for-beginners) | 导入文件 → 分段预览 → 选择索引/检索方式 → 处理 → 连接知识问答模板 | 补齐普通文件格式、分段预览和可替换嵌入/重排资源 |
| [LangGraph：自定义 Agentic RAG](https://docs.langchain.com/oss/python/langgraph/agentic-rag) | 加载/切分 → 嵌入/检索工具 → 模型决定是否检索 → 判断资料相关性 → 改写问题再检索 → 生成答案 | 把单次检索扩展成有次数、时间和费用限制的自我修正流程 |
| [LlamaIndex：构建工具调用 Agent](https://developers.llamaindex.ai/python/framework/understanding/agent/)（附[完整代码仓库](https://github.com/run-llama/python-agents-tutorial)） | 安装 → 定义带类型与描述的函数 → 注册模型和工具 → 执行多步任务 → 返回结果 | 可发现的 Tool Schema、模型选工具、工具回执、继续或停止判断 |
| [n8n：网站内容到知识问答](https://docs.n8n.io/build/integrate-ai/ai-examples/use-website-content)及[工具人工介入](https://docs.n8n.io/build/integrate-ai/ai-examples/human-in-the-loop-for-tools.md) | 获取网页 → 提取内容 → 向量入库 → 聊天查询；有副作用的工具展示参数并等待决定 | 受控 HTTP/连接器、可复用摄取流程，以及复用现有审批和恢复机制 |
| [Hugging Face smolagents：Agent 全流程指南](https://huggingface.co/docs/smolagents/en/guided_tour) | 选择 Agent 类型 → 选择远程或本地模型 → 注册工具 → 运行 → 检查记录并调整 | 模型后端可替换，结构化工具调用与代码执行分别声明能力；代码执行必须有隔离运行环境 |
| [Deep Agents：研究助手 Quickstart](https://docs.langchain.com/oss/python/deepagents/quickstart) | 配置模型 → 搜索工具 → 创建研究 Agent → 执行任务并输出报告 | 规划、上下文文件、子 Agent 分工和产物管理；细节参照其[能力概览](https://docs.langchain.com/oss/javascript/deepagents/overview) |

这些教程不是要求复制六套框架。应让相同的模型、工具、知识、状态和事件契约支持这些流程，并把常见流程做成可展开蓝图。

## 4. 补全优先级

以下优先级是调研建议，需纳入后续阶段范围后再开发。多数能力已经出现在现有完整清单，重点是实现和贯通。

### 第一批：普通用户能搭出实用 Agent

1. **通用工具循环与基本控制流。** 落实已有设计 `core.reason.tool_loop`、`core.reason.choose_action`、有界循环/逐项处理、工具错误与重试；复用现有预算、取消、审批、轨迹和检查点。为本地模块与受控 HTTP/搜索工具生成统一 Schema；之后再接入 MCP。不要把固定顺序“调用工具后生成回答”包装为动态工具决策。
2. **可编辑的知识摄取蓝图。** 将已有来源、同步、嵌入、索引能力接到现有设计 ID；先补 PDF、DOCX、表格与 OCR 适配器，再补分段预览、页码/位置引用。默认提供“导入资料→建索引→问答”的简洁入口，高级用户展开修改。
3. **模型资源分清职责。** 将生成、嵌入、重排、分类/评分等能力显式区分。优先打通受控自定义 Provider 和本地模型服务，再评估内置推理后端的安装大小、硬件与许可证。Ollama 官方已有[多轮工具调用示例](https://docs.ollama.com/capabilities/tool-calling)，可作为本地生成模型适配的行为参考。
4. **基础检索评估随 RAG 一起交付。** 提供用户问题集、预期来源、检索命中、引用正确性、延迟和用量对比。现有开发测试可以复用方法，但不能替代用户自己数据上的质量判断。

### 第二批：长任务和协作

5. **高级检索与记忆。** 神经重排、检索问题改写、证据不足再检索、语义记忆搜索、摘要和过期机制；组合能力优先形成蓝图，避免新增同义积木。
6. **多 Agent 与按需 Skill。** 补任务委派、交接、并行子任务、结果汇总及冲突策略；Skill 按需装载，MCP 工具权限沿用 Host。现有跨模块调用和纯计算并行应保留其明确语义。
7. **外部事件与多模态。** 按真实场景补定时/外部事件触发、数据库/表格连接器、图片理解、语音转写等；外部触发持久性复用工作流设计。

### 实验扩展：学习式决策与世界模型

“嵌入式模型”可能指 Embedding，也可能指装在本机运行的模型：前者已有锁定 E5，后者目前尚无通用本地生成后端。二者应在产品里明确区分。

用户提到的“jev”尚未确认，本记录暂按 JEPA/世界模型方向调研。Meta 官方仓库已发布 **V-JEPA 2.1**（2026-03-16），重点是视频/图像表征；**V-JEPA 2-AC** 是动作条件世界模型，官方示例涉及机械臂动作规划。它们不能直接等同通用聊天、商业规则或网页工具决策模型。[Meta 官方源码与说明](https://github.com/facebookresearch/vjepa2)

对 Blocky 更合适的路线是：先让“根据状态选择动作”接受规则或模型后端，再引入可检验的分类/评分策略；世界模型作为高级适配器试验“观察→编码→预测候选结果→评分→选择动作→执行→反馈”。需要新增的核心设计主要是模型能力描述、观察/动作/预测结果类型和模型工件生命周期。先在小型模拟环境验证收益，不承诺直接改善现有问答或 RPA。

## 5. 用三个完整作品决定是否补齐

后续实施可先用以下作品验证覆盖度，再据此确定正式验收项：

1. **个人资料助手：** PDF/DOCX/网页导入、增量更新、向量/混合检索、重排、引用回答、无证据时澄清；在用户问题集上比较配置。
2. **工具办事助手：** 自然语言任务、模型选择工具、参数校验、执行反馈、失败恢复、多轮继续、停止；涉及副作用时沿用已声明的权限与审批。
3. **规则与学习模型协作助手：** 规则处理明确情况，分类/评分或生成模型处理其余输入，无法可靠判断时走明确后备路径；可比较规则和模型的实际效果。

所有共享能力同时提供 GUI、CLI、Schema、结构化状态与可定位错误。框架名和模型品牌放在资源/适配器选择中；已有积木能够表达的流程优先复用。此调研未增加产品实现、依赖或技术债。
