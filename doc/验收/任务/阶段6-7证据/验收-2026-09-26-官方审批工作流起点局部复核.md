### 原生账本、审批和恢复

`workflow-run.test.ts` 各以独立 Node CLI 子进程执行创建、显式启动、审批预览、审批提交和继续。工作流步骤由 `--simulate` Runtime 输入驱动，但实际 native workflow helper 负责持久账本；本次没有外部业务副作用。批准与拒绝两种结果均通过；首次运行停在 `awaiting-approval`，业务决定先返回 `applied=false` 的预览，提供预览摘要后才可提交。过期/重复摘要收到 `BLK-WORKFLOW-CONFLICT`。继续使用不同的新输入后，输出仍取决于首次准备的状态；运行事件不包含首步 `remember`，不是从输入重新运行首段。

附加隔离资料目录探针用当前 debug helper 实际建立并读取 `profile/workflow/task-<id>.bin`。账本文件头为 `BLKWF1`，大小2812字节；合成输入不在文件明文中。workflow list/show 的序列化公开摘要同样不含合成输入。源代码中 Host 对文件正文经 `secret_store::crypt` 加密后再写入；当前探针读回了真实生成的账本密文，不尝试解密或触碰真实用户资料目录。

拒绝路径的 Runtime 定向用例观察真实 Block Runtime 状态，断言 `saved-input` 被清除、sessionMemory 为空且 `deliver` 未发生；CLI 新进程继续结果状态及结构化输出均为 `compensated`。因此补偿不只是写出标记。该用例的业务数据与端口为测试夹具；外部副作用不在本起点范围。
