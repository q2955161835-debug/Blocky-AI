## 详细报告

### 坐标声明与授权

TS Schema 只允许 coordinate+click 和 riskAccepted=true；非负整数、32767 数值上限及无额外字段约束继续有效。Rust Coordinate 使用 u32，Plan.validate 同样拒绝未接受风险、超过上限以及非 click 动作。fill/read/wait/find/screenshot 不能借坐标声明进入执行。

Host 的原生整体计划通过 input_policy::describe 展示“高风险坐标回退”、误点风险和 CSS 像素原点；授权成功后才启动页面并创建 session。grant.coordinateFallback 从已批准计划推导，用户仅填写 riskAccepted 不会直接得到 grant。逐步入口对 coordinate 再发独立原生确认，确认使用已保存步骤，不能从调用请求替换坐标。确认后重新检查 grant 有效期；取消仍走原有私有 worker/Host 结算路径。

本轮仅静态核对该调用顺序，并运行风险描述逻辑测试；没有点击真实原生允许/拒绝按钮，不把这些证据写成完整原生授权交互通过。

### Page、视口和执行绑定

BrowserHost.authorize 核对项目、随机 Page identity、计划目标、grant 目标及 action；计划含坐标时要求 coordinateFallback，保存该页面授权时的视口副本。perform 从已保存计划的 next 索引取得步骤，通过 token、stepId、期限、active/failed 状态约束后派发；调用者不能传入新坐标覆盖该步骤。

performBrowserCoordinate 在调用 page.mouse.click 前核对明确视口授权、当前宽高相等、整数和严格视口内范围，并检查 AbortSignal。坐标为页面可见视口左上角 CSS 像素，固定默认1100×760。风险提示正确说明页面布局变化可能误点；这不构成语义目标稳定性保证。

实际 headless 用例通过本机 HTTP fixture 和生产 BrowserHost：缺少 coordinateFallback 被拒绝；授权点击后状态计数为1；重复点击步骤被拒绝；x=1100 越界后计数仍1；新会话授权后将视口从1100×760改为1000×760，点击拒绝且计数仍0。单元另外核对负数、小数、NaN、缺失视口授权和预先取消均不调用 click。这里的 page.mouse 是浏览器协议派发，不操作系统光标。

Host 点击仍经过 effectKey/uncertain 写盘及既有回执顺序逻辑；BrowserHost 自身也只推进一次 next。已派发点击不能因后续取消撤销，原有未知结果保留机制继续适用。本轮没有扩大重验 journal/恢复整批。

### 桌面、CLI 与兼容边界

桌面只有 browser 分支显示独立高风险坐标组件；缺坐标、越界或未勾选时不能添加。X/Y 任一改动及成功添加坐标步骤后清除勾选，实际计划保留已审阅坐标并显示高风险标识。原生确认仍独立执行，组件勾选不代替它。

CLI validate 返回 coordinateSpace、风险 warning 与 requiresAttendedApproval，Schema 明确 CSS 像素及 Windows 不支持。普通块的权限计算在 TS/Rust 均增加 rpa.coordinate；实际 CLI 生成补丁后，省略该新增权限的接受请求被 native patch guard 拒绝，完整权限接受成功并保留 riskAccepted。其后实际执行仍需 Host 原生批准。

Windows preflight 仍只接受 UIA locator，worker 也拒绝非 UIA；本批没有新增系统屏幕坐标点击。CLI 对该声明明确发出 UNSUPPORTED 警告，不能将计划语法可校验描述为 Windows 坐标已可执行。
