## 详细报告

### 录制草案

#### 场景：正常输入与动作捕获

既有测试 4/4 通过，包括未知 value 字段拒绝、连续输入合并、manual-input 引用、敏感控件标记、重复定位拒绝、跨框架忽略、秘密样式定位词拒绝、停止后事件不改变草案。源代码未直接访问控件 value、键盘或剪贴板内容。草案不含执行 grant，且 `requiresReview=true`；这不证明后续未接入的原生审批流程。

#### P1-01：输入正文经页面元数据反射进入草案

- 位置：`browser-recording.ts:85`–`89` 的事件时 label 读取，以及 Host 回调唯一匹配后 append。
- 复现：本地 route 返回一个 textbox；页面先注册 input 捕获监听，在真实输入事件时把 `event.target.value` 写入该控件的 `aria-label`。随后启动录制并通过 headless Edge 实际 fill 合成正文。
- 实际：产生 1 个 fill 动作，`actions[0].locator.name` 与 `plan.steps[0].locator.name` 均含完整合成正文，`sensitive=false`、`omitted=0`。
- 证据：`try/stage7/recording-review/reflection.json`、`probe.test.ts` 第一项及 `probe.log`。断言“不包含合成正文”真实失败。
- 判断：不直接读取 value 不能保证 Typed value 不进入草案；恶意页面控制的动态可访问名称仍可能是用户输入。角色/名称唯一匹配只能确认 DOM 匹配，不能确认名称不是正文。
- 建议：避免将输入后页面提供的自由文本视为已验证安全定位元数据；对可录制目标采用交互前受控元数据绑定并拒绝交互中的名称变更，或使用不携带页面正文的受控定位表示。不要单靠增加秘密正则修复这一通路。修复须保留此反射负例。

### 录制时长与容量

#### 场景：有界录制

Buffer 在第 100 个动作封存、到期拒绝新动作，测试使用注入时钟验证 600000ms 边界。BrowserRecording 在进入异步定位前递增 queued，达到 32 后省略；在 finally 递减。省略计数上限 10000。该队列限制做了静态核对，未单独执行队列压力测试，不能将 Buffer 时钟测试写为真实 10 分钟浏览器结算证明。

### 停止录制

#### 场景：正常停止和导航

既有 headless 测试验证正常停止后点击不会改变草案，重复 stop 返回相同结果；主框架导航触发 target-lost 并最终停止。停止先关闭 Host 接收、移除导航/关闭订阅，再等待页面清理和已接受队列。

#### P2-02：页面可改写清理函数，使停止永久拒绝

- 位置：`browser-recording.ts:95` 将清理函数放入页面可写 window 属性；`:111` 调用该属性，错误时在封存/settled 之前退出。
- 复现：启动录制后，页面枚举 `blocky_record_*_remove` 属性并将它替换为抛错函数；调用 `stop('stopped')`。
- 实际：stop 拒绝；status 为 stopping，settled 未置位；已缓存的 rejected Promise 使后续 stop 不能重试，原 document 监听未由该函数移除。本测试使用同步抛错，不依赖无限循环或测试超时。
- 证据：`try/stage7/recording-review/removal.json`、`probe.test.ts` 第二项及 `probe.log`。
- 判断：Host accepting 已关闭，未发现该路径继续把动作写入草案或产生执行授权；问题是监听/会话无法正常结算，也没有可恢复的明确失败终态。
- 建议：清理控制不依赖可由页面替换的回调，增加有界、明确的失败结算或重试路径；不能仅吞掉错误并声称监听已经清除。
