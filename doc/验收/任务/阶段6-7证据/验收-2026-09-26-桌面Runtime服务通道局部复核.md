## 详细报告

### 1. 连续运行与私有数据

RemoteRuntime 对输入做严格结构校验，拒绝能力字段和任意路径，使用同一 Runtime 实现并以私有 state 字符串交接。并发 run 在 current 占用期间拒绝；debug 控制转发至当前 Runtime。正式测试覆盖连续状态、序号、真正 Node worker 调试和输入 EOF。该数据交接不是停止凭证或未知副作用恢复授权。

### 2. 服务白名单与人工输入

RuntimeServiceHost 按固定 service 名和字段集合派发。知识 context、agent input 和引用验证必须匹配当前 projectId；具体业务权限仍由原 adapters/原生端口执行。RPA 计划先经过 schema 和 browser origin/project 校验，inputSources 与 fill 步骤对应，敏感输入只允许 manual；perform 必须匹配已打开计划中的完整步骤。原生端口仍负责步骤顺序与实际授权。

正式负例验证坏计划/变造步骤不调用端口、重叠 open 拒绝、agent close 后新工作拒绝。人工 RPA 合成正文只经私有输入服务传递，事件和返回 state 中未出现正文。本轮未实际操作 Windows 或浏览器。

### 3. DESKTOP-SVC-P2-01：关闭超时后遗留迟到 RPA 句柄

位置：`packages/runtime-core/src/runtime-service-host.ts` 的 rpa.open await 后 `handles.set`，以及 close 的 pending drain。

复现：模拟 adapter.open 持续 pending；调用 host.close，推进假时钟 10 秒后 close 返回 BLK-RUN-SERVICE。随后 adapter.open 返回一个可关闭的句柄。原 request 此时仍成功返回 handle；独立 close spy 为 0 次。再次 close 只会取得已失败的 memoized closing Promise，无法回收新加入的句柄。

证据：`try/stage7/desktop-runtime-review/late-open.test.ts`、`late-open.log`；期望一次清理的断言失败，`lateHandleCloseCalls=0`。未创建真实 RPA 资源。

原因：open 仅在调用前检查关闭/取消，await 返回后不复核；close 超时退出后没有继续处理迟到资源。建议返回时复核 closed/abort，迟到句柄有界关闭后拒绝交付；若清理仍无法确认应返回失败而非伪报结算。本发现适用于内部服务基础，不宣称尚未接入的普通桌面已暴露此路径。
