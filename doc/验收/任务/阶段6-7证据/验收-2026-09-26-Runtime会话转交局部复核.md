## 详细报告

### 1. 连续会话与状态隔离

构造函数先 parse 整个状态，再构建 memory/mailbox，拒绝与显式 sessionId 不一致及外部 nextSequence 冲突。记忆键包含项目、会话、键名；队列按项目/通道保存原先顺序。解析后的普通数据来自 JSON 克隆，正式测试覆盖修改输入快照不影响恢复实例、恢复实例消费不影响原实例、跨项目不能消费他方数据，以及三个新 Node 进程间事件序号递增。

capture 在 running 时拒绝；debug 暂停仍处于 running，finally 才清理。EventMailbox 有 pending receiver 时拒绝 capture/restore，restore 先验证全部队列再赋值，非空队列禁止替换。导出类型不含 adapters/services/capabilities，不是 Job 停止证明、执行权限或业务未知效果恢复回执。

### 2. STATE-P2-01：数组继承行为突破纯数据校验

位置：`packages/runtime-core/src/workflow/protocol.ts` 的 workflowJson，Array.isArray 分支跳过 prototype 限制，随后 JSON.stringify；新 session-state.ts 直接复用此路径。

最小探针给合法状态的 memory 使用 Array 子类，原型定义 `get toJSON()` 并计数，返回空数组序列化函数。parseRuntimeSession 返回成功且 getter 调用一次：`invoked=1, accepted=true`。没有运行攻击载荷或读取秘密。

原因：仅检查 own property descriptor 能排除自有访问器，不能排除数组继承 getter/toJSON。状态校验因此执行了输入对象行为；即便当前没有公开导入端点，也违反本内部接口的“纯数据、不执行访问器”承诺。建议限制数组为标准原型，或从已验证 descriptor 安全构造普通数据后再序列化；补继承访问器负例。不得把既有 workflowJson 同类行为视为新调用边界已安全。

### 3. STATE-P2-02：导出拒绝实际已接受的运行数据

位置：`packages/runtime-core/src/session-state.ts` 的 `workflowJson(item.value, 32768)`；对照 `agent-execution.ts` 的 core.data.set / core.memory.write，现有运行写入仅校验 JSON/字节预算，未要求 32 层。

独立合成普通 state-machine 项目把 HANDLER 换成 core.data.set→session memory.write，保存仅 67 字节的 33 层数组。真实 Runtime.run 返回 completed，modelApiCalled=false；随后 captureSession 抛 BLK-RUN-STATE。不是伪造导入状态，也未触及字节预算。该状态在现有运行中合法，却无法通过新内部转交接口导出，将影响未来 worker 迁移。

建议统一实际写入和转交契约并补真实运行后导出用例，不能只测试人工构造的 state。若坚持 32 层新约束，应明确处理已接受状态及运行入口，避免执行结束才首次发现无法转交。

### 4. 预算和默认调用影响

workflowJson 新参数默认仍为 131072 字节、50000 节点、32 层；未指定新参数的旧工作流校验没有被整体放宽。会话外壳单独放宽到 36 层后，对逐条 payload/value 再执行原深度验证；session memory 用 encoded key 数组计算原 1 MiB 预算，队列 payload 合计 262144 字节、128 项、单项 16000 字节。正式测试覆盖 dense memory、32 层外壳、超限与额外字段；上述两项是本轮实际发现的例外。
