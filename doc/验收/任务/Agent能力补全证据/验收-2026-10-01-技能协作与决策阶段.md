## 详细报告

### 1. Skill 的安装、选择和实际工作

#### 场景：用户安装一个可发现的技能包，按需查看所选内容

实际目录提供 `blocky-skill.json`、`SKILL.md` 和 `scripts/run.js`，由正式 CLI `skill prepare/preflight/execute` 与真实 Rust Host 安装，另一个进程 discover 只返回元数据、摘要、版本、文件路径/哈希及字节数，不返回正文或代码。load 显式读取所选正文，read-resource 只读取包内声明且哈希锁定的附属资源。未选择的正文没有加入运行指令。

#### 场景：用户调用技能完成文本统计

安装包声明 `text-tool` 与不存在的 `ghost`。正式 CLI 的 Skill 积木只调用已注册且获准的文本统计工具，经过独立 Skill 和 tool 批准摘要，由真实 Host 对合成输入 `alpha beta gamma` 返回 `words=3, characters=16, lines=1`。附属 JS 含合成标记文件写入操作；安装、发现、加载、资源读取和实际执行后标记文件均不存在。此流程有实际用途，但没有声称执行附属脚本或模型摘要。

独立 Runtime 探针另加入已注册但未授予 `network.request` 的工具；加载的恶意正文要求扩权并运行脚本，最终工具交集仍仅 `text-tool`。所选版本和 digest 进入状态结果，普通工具入口继续检查权限与已选技能工具清单。

#### 场景：过期版本、越界路径或取消不能产生工具作用

实际 CLI 验证错误 digest、资源版本不匹配和未声明工具，均在真实工具作用之前失败；没有 tool 批准请求。原生目录 junction 和 `../SKILL.md` 被拒绝。批准摘要绑定完整请求，跨项目修改与 execute 重放被拒绝。独立取消探针在正文加载期间中止，后续工具调用次数为零；Rust 测试进一步覆盖损坏哈希、磁盘篡改、文件/总容量、原子保存和 profile 链接。

### 2. 子 Agent 的任务交接、并行与结算

#### 场景：初稿 Agent 将结果交给审阅 Agent

实际使用协作模块的模型积木，通过正式 CLI、既有用户模型引用和 Host 安全存储，顺序调用两个真实子 Agent。`draft` 与 `review` 各有不同 taskId、相同 parentTaskId、自己的角色指令、模型事件和结果来源。第二个子任务输入来自第一个已完成结果；独立模块探针实际检查第二次模型请求包含第一次输出。CLI 真实运行返回两个 completed 来源及两个 DeepSeek 响应回执。

共享输出预算显式设为 4096；每个所选 live-model 的请求上限为 1024。较小预算产生失败子任务是预算行为，不能把父运行完成状态单独当作两个子任务成功。首次预备运行的一次 API 回执因探针在断言后才保存而未保留；不编造该次用量，后续完整脱敏证据单独记录。

#### 场景：同模块的两个子 Agent 并行执行

独立模块运行支持并行及来源分离，但真实 CLI 初验发现两次模型请求使用同一 requestId，Host 拒绝第二次批准，返回一个 completed 和一个 `BLK-PERM-001` failed 来源。独立最小 Runtime 探针确认两个 requestId 均为 `run-…-collaborator-model-3`；纯替身允许两个相同 ID 请求，无法覆盖真实批准绑定问题。实现方最终采用同一 run 内同步递增请求序列，独立原失败探针 1/1 通过；正式工件也记录 distinct `-request-9/-request-10` 和两个实际响应，该问题关闭。

该修复经过两次工件集成负例：旧 worker 仍有重复 ID；更新 worker 后没有按同一顺序重编译 helper，Host 内嵌的 worker-lock 与实际 worker 不一致，整个 Runtime 通道失败而没有 API 外发。按 worker → helper → CLI 的顺序重建后恢复运行。证据分别是 [旧 worker](../../../../try/agent-capability-upgrade/d234-acceptance/live-worker-stale.json)、[worker-lock 不匹配](../../../../try/agent-capability-upgrade/d234-acceptance/live-runtime-channel-failure.json) 与 [最终序列 ID 源码定向复验](../../../../try/agent-capability-upgrade/d234-acceptance/parallel-sequence-id-isolated-retest.log)。

14:50 的真实并行有两个获准且成功返回的 API 响应，但 review 的输出被正常引用护栏 `BLK-GUARD-001` 拒绝；没有关闭护栏来通过。将合成创作输入明确限制为无引用、无出处后，14:54 的并行又返回一个 completed 和一个 `BLK-APPROVAL-BUSY` failed 来源，只发起一个批准与一个真实 API。Host 唯一对应错误来自 `approval_ledger.rs` 的 `try_lock()`；两条子任务进入短事务时竞争不能视为用户拒绝。证据：[护栏拒绝并保留用量](../../../../try/agent-capability-upgrade/d234-acceptance/live-parallel-guard-rejected.json)、[审批竞争失败](../../../../try/agent-capability-upgrade/d234-acceptance/live-parallel-approval-busy.json)。

修复把 ledger 短文件事务争用改为最多 5 秒等待，批准输入与网络请求不持有该文件锁。独立真实 helper 用 16 个进程并发 issue、16 个进程并发 consume 全部成功，随后 16 次并发重放全部以 `BLK-PERM-001` 拒绝，没有通过放开审批或重复消费修复。正式 CLI 同样的合成任务在 15:01 复验，两个 Agent 的 model.started 同为 15:01:00.333、分别 15:01:01.523/02.004 完成，两个来源均 completed、两个不同 API 响应回执可读回，批准竞争问题关闭。证据：[16 进程批准/消费/重放](../../../../try/agent-capability-upgrade/d234-acceptance/approval-ledger-concurrency-results.json)、[最终真实并行来源与时序](../../../../try/agent-capability-upgrade/d234-acceptance/live-collaboration-results.json)、[实际 CLI 退出 0](../../../../try/agent-capability-upgrade/d234-acceptance/live-parallel-ledger-retest.log)。

#### 场景：子任务权限、预算、失败及停止

独立执行全部任务权限预检；子权限超出父范围时零作用。实际子模块未获 memory.write 时新增写入积木被拒绝。共享 calls/output/steps/deadline 复用一个 RunBudget：并行输出预算只够一个模型时，仅一个模型端口调用，另一来源记录 `BLK-RUN-004`；没有各子任务重置预算。

顺序 stop 在首失败后将剩余来源标 skipped；collect 保留失败来源和稳定错误码，下一子任务使用最后有效输入。嵌套委派调用同一模块导出被 `BLK-TOOL-RECURSION` 拒绝，没有重复模型作用，轨迹保留失败来源。原生服务结算探针让两条已经开始的模型请求延迟返回后中止，最终等待两条请求均结算后发布 cancelled，没有部分成功或晚到正文。该取消证据使用正式 NativeAgentServices 加本地可控端口，未另外中断真实供应商请求。

证据：[真实顺序与初验并行](../../../../try/agent-capability-upgrade/d234-acceptance/live-collaboration-initial.json)、[并行 ID 失败探针](../../../../try/agent-capability-upgrade/d234-acceptance/parallel-request-id.log)、[基础 19/19](../../../../try/agent-capability-upgrade/d234-acceptance/baseline-ts.log)、[新增探针初验](../../../../try/agent-capability-upgrade/d234-acceptance/independent-runtime.log)、[构造修正后的两项复验](../../../../try/agent-capability-upgrade/d234-acceptance/probe-construction-final.log)。其中步骤与共享预算、取消结算采用受控本地端口，未宣称所有负例都调用供应商。

### 3. 规则与真实 CPU 候选评分

#### 场景：用户提供英文候选说明、阈值和后备标签

实际模型为 `ms-marco-minilm-l6-v2-int8-v1`，revision `a09144355adeed5f58c8ed011d209bf8ee5a1fec`，模型 SHA256 `e9d8ebf845c413e981c175bfe49a3bfa9b3dcce2a3ba54875ee5df5a58639fbe`，ONNX CPU cross-encoder。它对英文输入与候选说明做成对相关性评分，采用 pair truncate512；返回 **logit，不能称为概率或通用分类质量**。阈值需由用户结合任务校准。

正式 CLI 实际执行三个路径：大小写不敏感规则命中时不启动模型且无分数；没有规则命中时实际 CPU 推断地理候选；阈值 100 触发 `unknown` 与 `BLK-DECISION-BELOW-THRESHOLD` 后备，仍保留候选 logits。相同问题仅替换候选说明，得分可从 8.170721 变为 -7.588471，说明分数依赖输入和候选说明，不是类别固有可信度。

另一次独立真实 CPU 用地理及体育两种合成问题分别选中 geography 和 sports，记录模型版本、工件 hash、后端和耗时；这些少量示例只证明专用推理及路由链，不是准确率测试。正式 Runtime 的决策积木也实际返回 CPU record，未调用外部大模型 API。

#### 场景：非法或缺少模型时按声明处理

CLI 拒绝非英文文本、空/缺/越界阈值和单词标签说明；Schema 与绑定测试保留非整数阈值并拒绝混淆项目、请求、标签顺序、scoreKind 和概率声称。隔离的不存在模型目录实际触发 missing-model 后备，score 为 null、候选为空、errorCode=`BLK-EMBED-MISSING`。此时 backendInvoked 表示已尝试后端入口，不能声称已完成模型推理。

取消前校验不调用端口；Host 的取消期间单元探针在首个成对评分后设置取消标记，阻止下一对评分和结果发布。未另行实测真实 CPU 正在推理时的桌面取消或原生窗口生命周期。
