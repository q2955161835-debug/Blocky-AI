## 详细报告

### 1. 建立并冻结用户测试集

#### 场景：创建草稿、导入与冻结后重新读取

Host 独立探针通过原生 preflight/批准摘要/execute 保存冻结集，由后续独立 helper 进程读取，内容一致。列表仅返回 kind/key/revision。Host 冻结集不能覆盖、错误 CAS 不改变已存 revision。正式 CLI 已创建草稿、导入相同草稿、冻结为 revision 2 并由后续进程读回；篡改 frozen hash 被拒绝。初验只返回通用 `BLK-CLI-010`，修复后独立复验返回可定位 `BLK-EVAL-HASH`，不改旧版本。

证据：[原生跨进程资产记录](../../../../try/agent-capability-upgrade/e3-acceptance/host-results.json)、[探针](../../../../try/agent-capability-upgrade/e3-acceptance/host.ts)。

### 2. 批量执行与取消恢复

#### 场景：每个案例调用正常 Runtime，区分错答与执行失败

独立 Runtime 探针实际运行两个合法文本例和一个非法对象输入，两个例正常完成且分别正确/错误，非法输入以 `BLK-EVAL-INPUT` 逐例失败。正确率手算为 1/3，引用检查为 2/3；错答仍是已完成案例，不与执行失败混淆。该探针工具端口受控。

正式 CLI 后续使用实际 Host 文本工具运行四例：correct 与 after 正确，wrong 完成但错误，invalid 以 `BLK-EVAL-INPUT` 失败。报告显示 completed=3、failed=1，正确率 2/4=0.5、引用检查 3/4=0.75、无检索期待时 retrieval accuracy=null。初验 CLI 输出层把 usage 的三个 null 计数替换为 `[已脱敏]` 字符串而损坏报告 Schema；修复后从同一 Host 资产读取，三个计数均保持 null，严格 report Schema 校验通过。没有为验证输出格式重复运行已经结算的案例。

| 案例 | 实际执行状态 | 原作品正确性 | 第二版正确性 | 依据 |
|---|---|---|---|---|
| correct：alpha beta | completed | true | true | 实际统计 10 字符、2 单词、1 行 |
| wrong：gamma | completed | false | false | 原实际 1 单词与期待 2 不符；第二版输出也不匹配 |
| invalid：额外字段对象 | failed | false | false | Runtime 输入适配器拒绝，BLK-EVAL-INPUT |
| after：hello world | completed | true | false | 原实际 11 字符；第二版转换为固定 10 字符 |

本表验证评估工具的计分与版本差异，不声称四个合成例证明模型或作品的通用质量。

#### 场景：停止后保留 partial report，恢复只运行 pending 案例

初验发现 CLI 组合层用同一个用户取消信号构造 `NativeEvaluationStore` 与 `runEvaluation`。执行已结算后，存储的 `throwIfAborted` 拒绝写入 cancelled checkpoint 和 partial report，抛 `BLK-EVAL-CANCELLED`。既有 MemoryStore 的取消测试没有覆盖该原生存储组合。实现方把资产生命周期与批次停止分离，保留 NativeStore 本身的信号语义。

独立使用当前 CLI 正式组合层与真实 Host，在第一例 tool 批准时停止，已等待 Runtime 结算后保存 partial report 和 cancelled checkpoint，第一例 uncertain、其余三例 pending；资产批准的信号保持存活。然后正式 CLI 新进程通过 checkpoint-key 续跑，保留第一例 uncertain、不重新执行其工具，剩余三例按原 caseId 顺序结算，其中非法输入例独立失败。此取消/恢复失败已关闭；未知副作用没有被当成成功或自动重试。没有实际中止外部供应商请求。

证据：[初验失败](../../../../try/agent-capability-upgrade/e3-acceptance/independent-runtime.log)、[独立探针](../../../../try/agent-capability-upgrade/e3-acceptance/runtime.test.ts)、[实际组合层停止和 CLI 新进程恢复](../../../../try/agent-capability-upgrade/e3-acceptance/cli-initial-results.json)。

#### 场景：每例会话和授权在下一例前结算

实际 Runtime 两个案例分别申请不同 sessionId 的原生 grant，正常完成后各自 cancel grant，第二例开始时前例授权集合为空，最终没有 grant 残留。使用正式 NativeAgentServices 与可控原生端口；不声称实际桌面进程生命周期已验。现有适配器取消/执行结算、未知副作用不重放由独立既有测试补充。

证据：[契约修正后的两项独立探针](../../../../try/agent-capability-upgrade/e3-acceptance/probe-contract-final.log)、[既有 E3 定向 19/19](../../../../try/agent-capability-upgrade/e3-acceptance/baseline-ts.log)。

### 3. 冻结模型配置与比较作品版本

#### 场景：修改作品后不能继续旧绑定，fork 成新测试版本

正式 CLI 修改作品显示名、模型输出上限和输出转换后，旧集运行被拒绝且没有 tool 批准。初验只返回 `BLK-CLI-010`，修复后同一旧集负例返回 `BLK-EVAL-MODEL-BINDING`。fork 更新当前配置绑定并生成 version 2，冻结后 contentHash 与原四例集相同。第二版实际运行正确率 1/4=0.25，与第一版 0.5 可以手算比较。

初验把 CLI 返回的两版报告保存后交给 `evaluation compare`，因 null Token 被替换成字符串，两份报告都不符合报告 Schema，返回 `BLK-EVAL-REPORT-INVALID`。修复后独立由正式 CLI 读取既有成绩并保存，再运行 compare，实际 delta=-0.25、changedCaseIds=[wrong,after]、两版 candidate version 不同。比较后再读第一版，revision 仍为 1、完整内容不变；没有修改旧报告或重跑旧案例。

证据：[CLI 初验与问题](../../../../try/agent-capability-upgrade/e3-acceptance/cli-initial-results.json)、[既有资产读取/比较及两个错误负例 4/4](../../../../try/agent-capability-upgrade/e3-acceptance/cli-retest-results.json)。

### 4. 资产隔离与报告隐私

#### 场景：不同资料目录和项目不能读到原资产

真实 helper 下另一 profile、另一 projectId 的同 key 读取均为 null，修改获准请求的 projectId 被 `BLK-PERM-001` 拒绝。元数据列表不返回正文或资产 value。Host 原子替换失败、hardlink、CAS 竞争与不可变对象的既有测试由本 Agent 独立运行 6/6 通过。

#### 场景：报告只保留默认摘要，未知用量保持 null

正常评估路径默认存储 answerHash、structuredHash、检查结果与无正文的 generation receipt，不保存合成正文 canary。两例报告正确率 1/2，usage null 且 status unavailable，未以 0 声称已测量用量；模型评分 not-run 与人工评分空列表独立于确定性指标。

初验直接原生报告接口只校验 rows 数组、metrics/scoring 是 object，不校验逐例深层 Schema。独立探针在合法 report.rows[0] 添加未声明 `answer` 正文和 `apiKey` 合成凭据 canary，preflight 与 execute 仍返回 ok=true、revision=1 并持久化；类型化读取器之后会拒绝该资产。即使 TS 正常组合不生成这些字段，原生 IPC 边界仍接受了不符合报告 Schema 的资产。该负例使用合成值，不涉及真实秘密。

深层白名单修复后，独立在 debug 与最新 release helper 分别验证 7/7 场景：合法资产仍可持久化，report.rows 与 checkpoint.cases[].result 中 answer/apiKey 两字段分开输入，正式 preflight 和直接 execute 均返回 `BLK-EVAL-HOST-REQUEST`，目标资产仍为 null。该 Host 隐私/Schema 失败关闭。

CLI nullable Token 修复只允许三个明确用量字段的 null；独立脱敏探针确认 budget 的 reservedOutputTokens=null 仍脱敏，unknownToken、apiKey、inputToken 及 inputTokens 的字符串 canary 仍脱敏。既有报告读取和比较闭环同时通过，没有以放开任意 token 字段修复 Schema。

证据：[原生 release 7/7](../../../../try/agent-capability-upgrade/e3-acceptance/host-results.json)、[原始 Host 泄漏负例](../../../../try/agent-capability-upgrade/e3-acceptance/host-boundary-initial.json)、[独立既有 Host 6/6](../../../../try/agent-capability-upgrade/e3-acceptance/host-store-tests.log)、[用量 null 与秘密负例](../../../../try/agent-capability-upgrade/e3-acceptance/usage-redaction-retest.log)。初验 helper SHA256：`d74673451533e2af24a7b192cb5af7379104355a55173ba10d1bdde0f20de7d1`，37,697,024 字节，路径 `D:\1Folder\Blocky-AI\apps\studio-host\target\release\blocky-project-io.exe`。
