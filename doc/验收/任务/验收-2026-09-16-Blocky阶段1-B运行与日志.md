## 详细报告

### 1. 运行问答与解释执行状态

#### 1.1 配置、引用与取消

独立测试编辑角色为“教师”，观察模型适配器收到该值，最终回答生成对应标题；模型提出无来源引用时，该引用不进入回答。真实走 `parseProject → compileProject → Runtime → adapter`，未读取预录事件作为执行结果。适配器内部监听 AbortSignal，再主动触发取消，观察信号抵达、返回 cancelled、最后事件为 run.cancelled，且只有一个运行终态。既有聚焦测试另外验证无证据问题待核实、拒绝能力、资源 collection 变化、错误正文不进入事件及单工厂终态保护。

上述结论限领域接口；没有验证画布尺寸、减少动效或 UI 源块跳转。

#### 1.2 B-03：工具与模型异常未结算关联调用（P2）

分别注入抛错的知识和模型适配器。运行状态确实 failed，然而已经发出的 tool.started / model.started 没有同 correlationId 的 tool.failed / model.failed；实际仅产生 block.failed 与 run.failed，关联调用保持无终态。

依据：正式契约 `03-交互工具运行与可观察性-v1alpha1.md` 要求一次调用的开始、进度、结束由相同 correlationId 关联。影响：后续轨迹和日志消费者无法直接结算失败的调用。复现文件中参数化测试两项均失败。

修复方向：适配器调用边界独立捕获并产生关联失败事件，保留安全错误码；随后传播到积木和运行终态。

#### 1.3 B-04：多个 Runtime 实例生成重复进程事件序号（P2）

在同一测试进程依次创建两个 Runtime 并各完成一次正常问答，合计 40 个事件、仅 20 个唯一 sequence，两个实例都从 1 开始。原因是每个 Runtime 各自创建 EventFactory，而其计数器属于实例。

依据：正式契约 `03-交互工具运行与可观察性-v1alpha1.md` 第 70 行要求唯一工厂分配进程内单调、不重复序号。当前 runId 仍不同，本反例不声称 runId+sequence 的轨迹目标必然冲突；失败的是明确的进程事件序号契约。

修复方向：让生产 Runtime 使用共享、可注入的进程级事件工厂；确定性测试可显式注入隔离时钟/序号源。

### 2. 资源绑定与权限

#### 2.1 scope 和 secretRef 拒绝

将项目定义 scope 改为 user，保持引用为 project，资源解析拒绝 `BLK-RESOURCE-001`；将 secretBinding 指向未列入引用的虚构 secretRef，解析拒绝 `BLK-RESOURCE-002`。既有测试证明 user scope 不回退到项目定义。未读取本机真实凭据。

#### 2.2 B-01：权限由可编辑资源声明自行消除（P1）

复制正常项目，把 knowledge 资源的 capabilityRequirements 改为空数组，以 `Runtime({ capabilities: [] })` 运行。独立注入的同 ID 知识适配器被实际调用，`called === true`，应拒绝调用的断言失败。

编译器直接将资源的 capabilityRequirements 复制进 ToolContract.permissions；运行器只验证这份可由项目修改的数组。适配器注册表没有不可被项目降低的最低权限要求。因此调用者给出的空授权不能阻止项目擦除声明后调用原受保护能力。

本次证据是本地确定性知识适配器被越过权限调用，没有执行真实网络、文件或 Shell 副作用；不扩大推断为已经访问操作系统。修复应让可信适配器/Host 维护最低能力要求，资源声明可追加但不能缩减。

### 3. 日志与诊断导出

#### 3.1 B-02：结构化凭据未脱敏进入总线和导出（P1）

写入虚构的 `refresh_token`、`client_secret` 与嵌套 Cookie 字段。Cookie 正常被遮罩，但前两项的虚构值原样存在于 `bus.records` 和 `bus.export()`。即使该记录 redaction.applied=true，也仍有凭据字段泄漏。

原因：敏感键正则覆盖 token/access_token/secret 等少数精确键，遗漏上述常见凭据键。反例只使用明确虚构标记，不包含真实秘密。修复需覆盖对应凭据字段并复测总线、导出和事件入口；不能只在展示层遮罩。

#### 3.2 B-05：内容预算发生静默截断（P2）

对 17,000 个中文字符的 message 调用 redact。实现截取至 16,000 个字符，但 redaction.categories 仍为空，没有 oversize 或等价结构化截断标记。数组和对象同样按 1,000 项截断却无标记（代码证据；本次动态反例只执行字符串）。因此消费方不能识别记录已不完整。

本次另一个独立正例确认 RedactedBus 按实际 UTF-8 序列化字节数维持 1,000 字节预算，超过容量时 droppedImportant 增加。不能将此正例解释为终端输出预算、超时或完整通道保留均已通过；这些属于 E 批次。

修复方向：所有实际截断增加结构化截断元数据与原因，按约定记录原始/保留规模；保证导出不再次静默裁剪。
