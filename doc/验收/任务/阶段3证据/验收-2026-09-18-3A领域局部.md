对共享知识核心执行了以下检查：

- `packages/knowledge-core/tests/documents.test.ts:13-24` 验证 HTML 脚本和导航内容被排除、正文仍保留源行号；`:25-42` 验证插入前缀后相同正文的 `chunkId` 稳定且行号更新；`:43-55` 验证格式、二进制内容和非法分段预算拒绝。
- `packages/knowledge-core/src/documents.ts:101-109` 与 `packages/knowledge-core/src/sync.ts:30-38` 对分段大小和 overlap 做整数、范围及互斥校验；`packages/knowledge-core/src/store-schema.ts:91-110` 校验持久化索引的摘要、引用、ID 和分段关系。

### S3-02 增量更新与删除

基础增量行为通过了现有聚焦测试：`packages/knowledge-core/tests/sync.test.ts:77-104` 首次导入、重复同步跳过、正文修改更新及文档删除均通过；同时确认更新正文会生成新的片段 ID。实现中的复用和计数路径位于 `packages/knowledge-core/src/sync.ts:125-151`、`:186-190`，删除计数位于 `:206-209`。

发现 F-3A-01：部分来源失败时删除计数不对账。可复现步骤如下：

1. 用两个来源 `source-a`、`source-b` 完成一次同步，已发布索引含文档 `a`、`b`。
2. 保持两来源仍可见，只让 `source-b` 的 `readSource` 抛出普通读取错误。
3. 再次调用 `synchronize`。

验收探针输出为：

```json
{"status":"failed","counts":{"added":0,"updated":0,"deleted":1,"skipped":1,"chunks":1},"publishedDocuments":["a","b"],"pendingFailures":[{"sourceId":"source-b","code":"BLK-KNOWLEDGE-SOURCE"}]}
```

`status` 为 `failed` 且已发布索引仍包含 `b`，但 `counts.deleted` 为 `1`。原因是 `seen` 只在成功读取文档时增加（`sync.ts:120-124`），读取失败后来源进入 `pending.failures`（`:191-203`），最终删除统计却把所有未见旧键都计入（`:206`）。这会使任何读取此计数的上层对账把未删除正文报告为已删除。修复应使失败来源的旧键不参与本轮删除统计，或在失败结果中明确将删除计数标记为未结算。

### S3-04 取消同步、恢复与部分失败

现有测试证明了部分安全边界：`packages/knowledge-core/tests/sync.test.ts:105-120` 验证来源失败时旧已发布索引保留、失败被写入 pending、修复后可完成同步；`:137-150` 验证取消发生在写入前时不发布内容并拒绝损坏状态；`:151-172` 验证分页中止会留下包含第一页的 pending checkpoint。聚焦运行中这些测试均通过。

发现 F-3A-02：分页 checkpoint 不能真正恢复。可复现步骤如下：

1. 让来源返回第一页 `nextCursor=1`，在第一页 checkpoint 保存后取消。
2. 读回 pending，确认第一页已保存。
3. 使用同一端口重启 `synchronize`，记录每次 `readSource` 的 cursor。

验收探针输出为：

```json
{"cancelled":true,"checkpointDocuments":["one"],"firstRunCalls":[null],"restartCalls":[null,1],"resumedStatus":"completed","resumedDocuments":["one","two"]}
```

重启仍先调用 `cursor=undefined`，而不是从已保存 checkpoint 的下一页开始。实现每轮都在 `sync.ts:105-113` 将 cursor 和 snapshotRevision 重新置空；checkpoint 虽在 `:159-179` 保存，但 `pending.index` 没有 cursor 字段，`index.sources` 中已保存的 snapshot revision 也没有在下一轮读取，`completedSources` 同样没有在下一轮使用。`:72-84` 只把 pending 中已有的片段放入复用缓存，不能避免首页再次读取。此问题增加重复读取，并可能在来源分页内容变化时失去同一快照；不满足“取消并重启”的可复现分页恢复要求。修复应持久化每个未完成来源的 cursor，并在重启时读取已保存的 snapshot revision 继续该快照，或明确跳过已完成来源并保留可验证的恢复状态。

发现 F-3A-03：失败清单和重试范围未在组件中完整可见。`KnowledgePanel.tsx:36-40` 只把 pending 失败投影成“几个来源失败”，`:167-169` 只显示通用的“部分来源失败”提示，没有 source ID、失败 code、失败来源名称或可辨认的重试范围。S3-04 要求失败清单与重试范围可见，因此当前组件只能证明“未静默宣称成功”，不能证明用户可以定位并处理具体失败来源。

KnowledgePanel 的忙碌和清理行为单独探针通过：点击“同步资料”后，`KnowledgePanel.tsx:58-78` 设置忙碌态、阻止并发并在 finally 清理；`:174-181` 的“停止同步”同时中止本地信号并发送 `knowledge-cancel`；`:42-55` 在组件卸载时中止并发送取消。探针确认添加/同步按钮在同步中禁用、停止按钮可用、停止后同步按钮恢复可用且发出了取消调用。该结果仅为 React 组件级证据，未覆盖 Rust Host 是否及时结束原生读取或进程。

### F-3A-02 分页取消、checkpoint 与重启

```json
{"cancelled":true,"checkpoint":{"source-a":{"revision":"snapshot","nextCursor":1}},"restartCalls":[{"cursor":1,"snapshot":"snapshot"}],"status":"completed","documents":["one","two"]}
```

重启只读取下一页并携带相同 snapshot revision，最终发布两份文档。当前实现还会复用未变化的已完成来源 checkpoint；来源 revision 不匹配时不会走恢复路径。持久化结构由 `types.ts:71-76`、`store-schema.ts:71-99` 约束，损坏 checkpoint 仍由统一状态校验拒绝。
