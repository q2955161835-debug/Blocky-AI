### 1. 已通过的组件/项目模型行为

- Inspector 的“角色与指令”修改进入当前 Project 的真实 Workspace，`ProjectController.undo()` 恢复原值。

### 2. C-01：同一 `projectId` 重开后会话没有按新模块集合清理

这是组件级可复现的会话恢复缺陷，不涉及 `workspaceRef` 文件读取边界。

复现输入（临时文件 `try/accept-stage1-c/same-project-reopen.test.tsx`，已删除）：

```ts
const next = createStarter();
delete next.workspaces["citation-service"];
next.manifest.modules = next.manifest.modules.filter(
  (m) => m.moduleId !== "citation-service",
);
io.open.mockResolvedValue({ project: next, handle: "same-project" });
const hook = renderHook(() => useStudio());
// 等待初次编译后：
act(() =>
  hook.result.current.setSession((s) => ({
    ...s,
    tabs: ["citation-service"],
    active: "citation-service",
  })),
);
await act(() => hook.result.current.open());
await waitFor(() =>
  expect(hook.result.current.snapshot.project.manifest.modules).toHaveLength(1),
);
expect(hook.result.current.session.tabs).toEqual(["research-agent"]);
```

实际失败：项目模块数已变为 1，但 `session.tabs` 仍为 `["citation-service"]`，断言收到旧目标。`useStudio.ts` 的加载 effect 只在 `sessionLoaded.current !== projectId` 时执行；重开同一 `projectId` 时不会再次调用 `restoreSession`。由于 `App.tsx` 会过滤掉不存在的模块，用户可能得到空画布，且持久化会话仍短暂携带已失效标签。契约要求会话标签目标引用当前模块，重开后应按新 Project 重新校验。

### 3. C-02：未知版本和失效目标被静默处理，没有信息级诊断

复现文件 `try/accept-stage1-c/session-boundary.test.ts` 已删除。实际读回摘要为：

```json
{
  "unknown": {
    "tabs": ["research-agent", "citation-service"],
    "active": "research-agent"
  },
  "stale": {
    "tabs": ["citation-service"],
    "active": "citation-service"
  },
  "digestUnchanged": true
}
```

`restoreSession(project, { schemaVersion: "blocky.workspace-session/v99", ... })` 静默回退默认会话；当前返回类型只有 `Session`，没有可读诊断。v1 会话中的 `targetId: "missing"` 会被正确跳过，但也不产生信息级诊断。项目契约 `01-项目模块与会话-v1alpha1.md` 明确要求未知版本停止消费并返回可操作诊断，恢复时找不到目标要跳过并产生信息级诊断；当前实现只满足“不按显示名猜测”和“失效标签不进入 tabs”，不满足诊断要求。

该探针的断言要求 `unknown.diagnostics` 与 `stale.diagnostics` 存在，退出码为 1，失败行为为 `expected undefined to be defined`。同一探针确认会话处理没有改变项目摘要，因此这不是项目事实污染问题。

### 4. C-03：保存挂起期间运行命令状态与实际门禁不一致

复现文件 `try/accept-stage1-c/busy-command.test.tsx` 已删除：在 jsdom 中渲染 `App`，点击“新建项目”进入编辑器，再让 `saveProject` 返回未解决 Promise，点击“保存”，随后读取顶栏 `▶ 运行` 按钮。

```text
期望：顶栏 ▶ 运行按钮 disabled === true
实际：disabled === false
```

当前 `479731c` 的 `useStudio.run()` 已增加 `ioBusy` 保护，所以点击该按钮不会并发启动运行；但 `App.tsx` 的 `enabled("run.start")` 没有检查 `s.busy`，UI 仍把命令显示为可用，形成“按钮可点击、动作静默无效”。基线 `7862267` 没有该 `run()` 的 `ioBusy` 门禁，命令状态问题在基线同样存在；当前父任务提交只降低了实际并发风险，没有修正状态表达。

该探针退出码为 1，失败断言实际收到 `false`。jsdom 还输出 Blockly 依赖的 `HTMLCanvasElement.getContext()` 未实现提示，但测试已完成渲染并到达按钮断言；未将该环境提示当作产品视觉证据。

### 5. 命令定义与范围边界

`packages/command-system/src/index.ts` 提供带 `schemaVersion`、`commandId`、分类、默认快捷键、上下文、选择范围、危险等级和撤销属性的 `CommandDefinition`；`App.tsx` 与 `StudioDialog.tsx` 共同消费同一 `commands` 数组和 `enabled/execute` 路径。撤销、重做、返回、运行和文件操作的已实现回调可由组件调用。

命令包自身没有测试文件；直接运行 `pnpm exec vitest run packages/command-system --reporter=verbose` 退出码 1，Vitest 报告 `No test files found`。这属于覆盖缺口，不把“无测试文件”误报为实现测试失败；C-03 的按钮状态由独立 App 组件探针实际复现。
