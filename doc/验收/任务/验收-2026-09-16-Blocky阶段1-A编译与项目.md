### 4. 初验直接问题与复现输入（`bced3ec`）

以下问题均在初验候选提交 `bced3ec` 上复现，验收探针仅放在 `try/acceptance-stage1-a/`，执行后已删除文件；初验没有修改实现代码。复验使用相同输入核对修复结果，详见前面的“复验记录”。

#### F-01（高）：编译器没有交付计划要求的分层正式接口

实施计划规定 A 对外提供 `parseProject`、`compileWorkspace`、`linkProject`、`projectInteraction`。当前 `packages/compiler/src/index.ts` 只导出 `compileProject(input)`；后面三个编译/链接/交互边界没有独立 API。`parseProject` 和 `createSession` 在 `project-model` 中存在，但 `compileWorkspace`、`linkProject`、`projectInteraction` 不存在。

这使后续消费者只能依赖一个同时编译 Workspace、收集交互/工具并链接项目的巨型入口，无法按正式契约独立验证每个模块编译、链接结果和交互投影。它是接口契约未闭合，不由 24 个绿色测试抵消。

#### F-02（高）：链接有错误时仍把无效链接写进 ProjectIR

复现输入：

```ts
const p = createStarter();
p.manifest.modules[1].exports = [];
const result = await compileProject(p);
```

实际输出摘要：

```text
diagnostics = ["BLK-LINK-002"]
result.ir.links = [{ target: { moduleId: "citation-service", exportId: "lookup-v1" }, ... }]
```

类型冲突 `BLK-LINK-004` 和不存在模块 `BLK-LINK-001` 也分别复现相同形状：诊断正确，但 `ir.links` 仍保留对应无效边。实现中 `validLinks` 只用于同步环检查，而构造 ProjectIR 时使用原始 `links`。契约要求链接解析失败，且同步环使同步链接集合失效；当前 ProjectIR 没有有效性标记，独立消费者拿到的边仍像可执行链接。

#### F-03（高）：调用积木字段没有 StableId 校验，非法值进入 ProjectIR

复现输入：把 `research-agent` 中 `call-citation` 的 `fields.MODULE` 改成 `"C:/outside"`。实际输出为：

```text
diagnostics = ["BLK-LINK-001"]
result.ir.links[0].target.moduleId = "C:/outside"
```

`target.moduleId` 已违反 StableId 和项目引用边界，但仍从 Workspace 字段原样进入 ProjectIR。`MODULE`、`EXPORT`、`INPUT`、`OUTPUT` 目前只做存在/非空检查；链接目标的 ID 与 Schema 引用应在生成链接前按稳定 ID/相对引用校验，非法链接不得进入 ProjectIR。

#### F-04（边界待验收）：Manifest workspaceRef 的真实文件读取未在本批次验证

在当前 `Project` 内存 API 中，`workspaces` 是按 `moduleId` 加载好的 Workspace record，`workspaceRef` 是持久化布局映射；仅修改内存对象的 `workspaceRef` 不能证明文件读取错误。该批次没有实际 `.blocky` 编码/解码或 Host 文件读取端口，因而不能把下面的探针当成 A 的实现缺陷：

```ts
const p = createStarter();
p.manifest.modules[0].workspaceRef = "workspaces/other.workspace.json";
const result = await compileProject(p);
```

该内存探针输出 `diagnostics=[]`，且仍按 `workspaces["research-agent"]` 编译，这是当前 API 边界的预期现象。真实文件读取必须在项目格式/Host 解码时按 manifest 的精确 `workspaceRef` 打开，并对缺失文件拒绝；留待后续 C/项目格式边界验收核对。

原先将此现象写成“workspaceRef 未绑定”的高严重度缺陷，现更正为未覆盖边界，不计入本批次失败项。

#### F-05（高）：模块导出声明没有与 Workspace 的导出入口闭合

```ts
const p = createStarter();
p.workspaces["citation-service"].blocks.blocks[0].fields!.EXPORT =
  "unrelated-export";
const result = await compileProject(p);
```

保持 manifest 导出仍为 `lookup-v1` 时，实际输出为 `diagnostics=[]`，调用链接仍指向 manifest 的 `lookup-v1`，没有任何导出入口不一致诊断。这允许 manifest 宣称一个导出、Workspace 实际暴露另一个导出。跨画布导航和运行时按稳定 `exportId` 查找时可能定位不到目标；导出 ID 需要由链接器或 Workspace 编译器核对。
