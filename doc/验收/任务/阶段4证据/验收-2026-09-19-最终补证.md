## 详细报告

### S4-02 配置提示与上下文

#### 场景：完整 Runtime 到类型化 Host 请求捕获

独立探针从可编译项目实际运行 `Runtime → AgentExecution → nativeAgentServices → provider-preflight/provider-call`，没有直接调用纯字符串拼接函数冒充完整流水线。公开虚构标记分别进入角色、补充指令、项目记忆、登记工具结果、检索引用和用户输入。捕获结果为严格两条消息且顺序为 `system → user`：角色和可信补充指令只在 system；记忆、工具结果、证据及用户输入均只在 user 的 `<context-data>` 数据边界或其后的用户输入区。system 不含任一 `UNTRUSTED_` 标记；provider-preflight 与 provider-call 的类型化 request 完全相等，项目、秘密引用和 128 Token 上限均按资源配置进入请求。

既有边界测试负责 32 KiB 拒绝，本探针补足完整运行与请求捕获，两者合并满足该项；没有据此声称模型天然抵抗所有语义注入。

### S4-04 处理模型服务错误

#### 场景：打包 CLI 的实际错误投影

在项目内隔离的 `LOCALAPPDATA` 中，仅用 candidate3 打包 CLI 登记虚构 DeepSeek 用户资源，不导入任何秘密。先按真实摘要批准本机 `text.analyze/v1`，随后模型预检因秘密缺失在本地失败。JSONL 实际产生 `model.started → model.failed → block.failed → run.failed`，各失败事件稳定投影 `BLK-PROVIDER-CONFIG`；最终 `status=failed`、`generations=[]`、`modelApiCalled=false`，进程非零退出，未出现供应商正文或输入正文泄漏，也未发起网络请求。

401/403、429、500/503、302、坏 JSON、缺字段、完成原因非正常、响应过大、超时及取消由已有冻结 Rust transport 固定证据覆盖；`f24aea0` 相对原冻结实现未修改 `apps/studio-host`，因此复用该专项，不重复本地 HTTP 全矩阵。GUI 的本地拒绝可见投影由独立 GUI 报告覆盖。

### S4-05/S4-08/S4-12 直接影响

#### 场景：同一模型模块在同一运行中被调用两次

初始独立探针构造两个不同 `core.module.call` 依次进入同一个含 `core.model.compose` 的模块，确认可达且实际调用 generate 两次，但两次 requestId 都是 `repeat-run-shared-compose`。这会与一次性批准 ledger 冲突，初始结果为 1/2 失败，属于真实产品缺陷。

主 Agent 将模型及知识调用 correlationId 改为包含 `runBudget.calls + 1` 的运行内单调序号，并把该场景纳入正式边界回归。独立复验在冻结提交 `f24aea0` 上为 2/2 通过：两个 Provider requestId 唯一，且 generation、`model.started`、`model.completed` 三处 ID 一致。该修复没有增加重试、绕过批准或改变外发端点。
